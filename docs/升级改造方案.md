## 0. 执行摘要

**一句话诊断**：工程骨架（FastAPI 分层 + 真 LangGraph + 健壮 LLM 降级 + SQLite 持久化 + 104 测试 + CI/CD 上线魔搭）已达**扎实的准生产级 demo**；但支撑参赛叙事的两大核心卖点——"真实数据"与"7 个 AI 数字员工"——目前**严重注水**，且文档存在多处互相矛盾口径与一处政治表述错误。项目当前状态是"**能跑、能看、但经不起评委追问**"。

**综合健康度**

| 维度 | 评分(10) | 定性 |
|---|---|---|
| 后端架构与工程 | 6.0 | 家底扎实，有真东西 |
| AI 真实性 | 4.0 | 底座真、7 Agent 仅 2~3 个真用 LLM |
| 数据真实性 | 2.0 | **全静态假数据 + random，零外部管道** |
| 安全 | 3.0 | 机制齐全但默认全 fail-open |
| 前端体验 | 6.5 | 有路演质感，但 mock 兜底让错误态成死代码 |
| 部署 CI/CD | 5.0 | 能上线，但脆弱、无回滚、密钥进镜像 |
| 参赛文档 | 4.0 | 体量大，但口径打架 + 政治表述写错 |
| **加权总分** | **≈4.4** | **及格线上、名次线以下，改造空间巨大** |

**三大致命伤（评审现场最可能被一击穿帮）**

1. **数据注水**：`data/sources.py` 用 `random.randint` 冒充 Amazon/Alibaba 数据，义乌指数是常量 `102.8`；而前端页面底部却打印"数据来源：义乌指数·海关总署·Eurostat·世界银行"。评委问一句"这些数字是真的吗"即崩。
2. **AI 名不副实**：`compliance / smart_selection / supply_chain / policy_replication` 四个 Agent 文件里 `llm` 出现次数为 **0**，"智能"是 `random` + 静态字典；与"1 人 + 7 个 AI 数字员工"叙事直接冲突。
3. **文档自相矛盾**：盈亏平衡 4 个答案、12 月营收 4 个数、定价 7 套（同名档位差 10 倍）、"六个坚持"4 个版本且**在评委必读的 OPC 商业计划书 + 必看视频脚本里写错**——这是可能直接影响资格的单点高危。

**改造总策略（按投入产出比分四档）**

```
P0 止血（消除翻车点）  →  P1 做实（打造真亮点）  →  P2 强筋（工程与体验）  →  P3 商业化（产品落地）
   1~2 天，必做              3~5 天，决定名次           有余力/赛后              长期
   低成本高回报              中成本高回报               中成本中回报            高成本长回报
```

**核心建议**：不要试图把所有假数据都做成真的（工作量不可控），而是采取**"诚实化 + 单点做透"**组合拳——先用 P0 把所有"会说谎的地方"改成"可自证 / 明确标注演示"，消除翻车风险；再集中资源把 **1 个数据源 + 2 个 Agent** 做成真实可跑的样板，形成"这是真的、其余是产品规划"的可信叙事。

## 1. 现状评估

### 1.1 已经做对的（这是家底，改造要保护）

- **LLM 底座真实且健壮**：`services/llm.py` 接入阿里云百炼 DashScope（OpenAI 兼容，`qwen-plus`），实现了备选模型降级 + 半开熔断（连续失败 3 次冷却 10 分钟）+ 每日限额落盘 + 推理模型自愈（空内容放大 max_tokens 重试）。这是全项目工程质量最高的一块。
- **真 LangGraph 编排**：`agents/workflow.py` 用了 `StateGraph` + 7 节点 + 条件边 + `compile().ainvoke()`，非顺序包装；无 LangGraph 时降级 `_run_sequential`。
- **真持久化**：`db/database.py` SQLite WAL 模式，5 表（users/chat_sessions/chat_messages/api_usage/query_history）带索引。
- **测试有真集成**：104 用例，`test_routes.py` 用 `ASGITransport` 打真实 app + 临时库；LLM 测试用 monkeypatch 验证真实降级/熔断/落盘分支。
- **CI/CD 真跑通**：GitHub Actions（CI + Deploy to ModelScope + 5 分钟 keepalive + 部署后冒烟测试），最新提交全绿、已上线。
- **文档体量惊人**：14+ 篇 md/docx/pdf、两版路演 PPT、答辩 QA、财务模型、风险预案（质量最高）、**BP 数字溯源表**（全项目最诚实的资产，用三星置信度自曝短板）。

### 1.2 核心矛盾详解

| 矛盾 | 表现 | 根因 |
|---|---|---|
| 叙事 vs 实现 | 宣称 7 AI 员工 / 210 万 SKU 实时 / 39 城，实际 2~3 Agent 真 AI、数据全静态、mock 仅 12 城 | 先写 BP 后补 demo，实现未追上叙事 |
| "有 CI" vs "CI 被架空" | `flake8 ... \|\| true`、eslint `--max-warnings=999`、deploy 不 `needs: ci` | 为快速上线放宽门禁后再未收紧 |
| "AI 已接入"徽章 vs 静默降级 | 只要 HTTP 200 就显示"实时数据·AI 已接入"，无 key 时后端静默返 None 仍显绿灯 | 前端缺三态（真/降级/演示）判定 |
| OPC"1 个人" vs 答辩自认 | 答辩 QA 手册写"已有 2 名兼职工程师协助开发" | 材料未统一口径 |

## 2. 改造总纲

**三大原则**

1. **诚实优先**：任何"会说谎"的 UI/文档（绿灯、假统计、错误口径）要么做成真的，要么明确标注"演示数据/规划中"。评委最恨的不是"还没做"，而是"假装做了被拆穿"。
2. **单点做透**：资源有限，与其把 5 个数据源都做成半真，不如把 **1 个数据源接真 + 2 个 Agent 做出真智能**，形成可现场自证的样板。
3. **可自证**：每个亮点都要能"当场演示给评委看请求-响应"，而不是截图/PPT 承诺。

**改造范围**：后端 8 项、前端 6 项、部署 5 项、文档 6 项，共 25 个改造点，分 P0~P3 四档。

## 4. 关键战略决策（需你拍板）

### 决策一：诚实路线 vs 包装路线

| 路线 | 做法 | 优 | 劣 | 建议 |
|---|---|---|---|---|
| A 全做实 | 5 数据源全接真、7 Agent 全真 AI | 叙事完全成立 | 工作量 L×N，赛前不可能 | ❌ 不现实 |
| B 全诚实化 | 主动降口径为"3 LLM Agent + 4 规则引擎 + 1 真数据源" | 快、稳、真诚换信任 | 卖点"缩水" | ✅ 保底 |
| **C 组合（推荐）** | **P0 全诚实化止血 + P1 单点做透(1 数据源+2 Agent 真) + 口径与实现严格对齐** | 既消除翻车又有真亮点，可信度最高 | 需 4~6 天集中投入 | ⭐ **强烈推荐** |

### 决策二：改造与比赛时间线的关系

- **赛前**：只保 P0（必做）+ P1 中"能在演示时自证"的 1~2 项（P1-1 数据源样板、P1-2 挑 2 个 Agent 做真）。
- **赛后/持续**：P2、P3 按产品化节奏推进，对应你 `里程碑规划.md` 的 M1~M3。

## 7. 一句话结论
